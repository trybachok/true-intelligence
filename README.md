# Аналитический кабинет «Истинный интеллект»

Кабинет помогает клиентам отслеживать показатели присутствия своих филиалов на геосервисах.

## Функциональные требования

### Вход и доступ к данным

- Система поддерживает вход пользователей с ролями администратора и клиента.
- Администратору доступны данные всех компаний и филиалов. Клиенту доступны только данные его компании и её филиалов.

### Аналитика и филиалы

- Дашборд показывает количество просмотров карточек, переходов на сайт, звонков и построенных маршрутов, а также среднюю оценку и количество отзывов.
- Пользователь может просмотреть список доступных филиалов, выбрать один филиал или получить сводку по всем доступным филиалам.
- Пользователь может выбрать период. Итоговые показатели и график динамики одного показателя учитывают выбранные филиалы и период.

### Расчёт показателей по отзывам

- Количество отзывов за период равно числу отзывов, опубликованных за этот период в выбранных филиалах.
- Средняя оценка за период равна среднему арифметическому оценок в той же выборке. В сводке каждый отзыв имеет одинаковый вес. Два отзыва с оценкой 5 и восемь с оценкой 4 дают среднюю оценку 4,2 и количество отзывов 10.
- При отсутствии отзывов API возвращает количество `0` и среднюю оценку `null`. Для средней оценки интерфейс показывает «Нет оценок».
- Дашборд учитывает отзывы независимо от статуса обработки.

### Получение данных и демонстрация

- Интерфейс получает данные через REST API. Система хранит пользователей, компании, филиалы, ежедневные показатели и отзывы в PostgreSQL.
- Для демонстрации подготовлены данные минимум для двух компаний, трёх филиалов и двух пользователей с разными ролями.

### Дополнительные функции

- **Модуль отзывов.** Пользователь может просматривать доступные ему отзывы и фильтровать их по рейтингу и статусу обработки.
- **Импорт статистики.** Система получает статистику из имитации внешнего API, сохраняет её в PostgreSQL и корректно обрабатывает повторные запросы.

## Нефункциональные требования

- **Безопасность.** Сервер проверяет права при каждом запросе к защищённому API, включая прямые запросы. Интерфейс показывает данные в пределах прав пользователя.
- **Надёжность хранения.** Сохранённые данные доступны после перезапуска приложения. Схема базы разворачивается миграциями.
- **Обратная связь.** Интерфейс показывает состояние загрузки и сообщает об ошибках получения данных.
- **Воспроизводимость запуска.** README содержит инструкцию по настройке окружения, запуску сервисов через Docker Compose, применению миграций, загрузке демонстрационных данных и запуску тестов.
- **Тестируемость.** В проекте есть минимум два автоматизированных теста. Как минимум один проверяет изоляцию данных компаний через API.
- **Демонстрационные данные.** Используются только вымышленные данные. Для запуска достаточно локальной конфигурации без реальных клиентских данных, ключей внешних API и доступов заказчика.
- **Масштабирование.** До разработки функций схема PostgreSQL проектируется с учётом роста до 500 и более компаний и нескольких тысяч филиалов. При проектировании учитываются запросы по компании, филиалу и периоду. К сдаче готовится описание подхода к масштабированию.
- **Технологии.** Клиентское приложение использует React, Next.js и TypeScript. Серверное приложение использует Node.js и NestJS. Образы приложений используют Node.js 26.13.1 LTS. Данные хранятся в PostgreSQL. Все сервисы запускаются только в контейнерах Docker через Docker Compose.

## Запуск сервисов

```bash
docker compose --env-file .env up --build --watch
```

Команда запускает сервисы с демонстрационной конфигурацией и включает обновление контейнеров при изменении исходников.

- Фронтенд — [http://localhost:3010](http://localhost:3010).
- Бэкенд — [http://localhost:3020](http://localhost:3020). Проверка подключения к PostgreSQL — `GET /api/health`. На странице фронтенда её запускает кнопка «Проверить подключение».
- PostgreSQL доступен внутри Compose по адресу `db:5432`. Имя базы, пользователь и пароль задаются в файле окружения.

### NestJS Observe

Для подключения мониторинга задайте `OBSERVE_APP_KEY` и `OBSERVE_APP_SECRET` в `.env`. Получить их можно командой 
`npx @nestjs/observe@latest link` из каталога `backend` и подтверждением кода в браузере. 
Если ключи не заданы, Observe не подключается.

Compose применяет миграции TypeORM из `db/migrations` по порядку. Первая создаёт схему, вторая загружает вымышленные данные.
После успешного завершения сервиса `migrate` запускается NestJS. Дни отчёта и границы периода определяются по UTC.

```bash
docker compose --env-file .env run --rm --build migrate
```

Команда применяет новые миграции. TypeORM хранит версии обеих миграций в таблице `migrations` и пропускает уже применённые.

```bash
docker compose --env-file .env run --rm --build migrate npm run migration:revert
```

Команда откатывает последнюю применённую миграцию. В исходной схеме первый вызов удаляет демонстрационные записи, второй удаляет таблицы кабинета вместе с их содержимым. Для ручного отката сначала остановите бэкенд. Если демонстрационная миграция была применена до перехода на автоматические идентификаторы, откатите только её и затем примените миграции повторно.

## Контракт и тесты API

Спецификация OpenAPI находится в `contracts/openapi.yaml`. Она описывает реализованные технические маршруты и целевой контракт кабинета. Для прикладных операций в ней указаны параметры, проверка прав, форматы ответов и ошибки. Обновляйте её в одном изменении с сервером и клиентом.

```bash
docker compose --env-file .env exec backend npm test
```

Команда запускает модульные тесты в контейнере бэкенда.

```bash
docker compose --env-file .env exec backend npm run test:e2e
```

Команда запускает HTTP-тесты, в том числе проверку ответов при доступной и недоступной базе.

## Проверка схемы на целевом объёме

Планы запросов проверены через `EXPLAIN (ANALYZE, BUFFERS)` на синтетических данных PostgreSQL.
Выборка охватывала 525 компаний, 3 150 филиалов, год ежедневных показателей и 52 отзыва на филиал.
Запросы за 30 дней по филиалу и компании использовали индексы с идентификатором филиала.
Для сводки администратора индексы по дате сократили число обращений к буферам с 7 169 до 685 для просмотров и с 1 531 до 163 для отзывов.
Это сравнение планов на конкретной выборке. При другой глубине истории и распределении данных планы нужно измерять заново.
